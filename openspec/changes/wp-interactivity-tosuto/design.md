## Context

This is a greenfield WordPress plugin (`wp-tosuto`) targeting WordPress 6.9+. The plugin provides a toast notification component built entirely on the Interactivity API — no jQuery, no React on the frontend. The Interactivity API provides reactive state management via stores, declarative directives (`data-wp-*`) in server-rendered HTML, and automatic DOM updates. The design follows Shadcn's philosophy: minimal, composable, themeable via CSS custom properties.

The plugin consists of a single WordPress block (`wp-tosuto/toaster`) that acts as the toast container. The plugin renders this block automatically on `wp_footer` at a late priority. If the request-scoped queue is non-empty, the block is always rendered. If the queue is empty, the `wp_tosuto_render_empty` filter decides whether to still render an empty container (so JS-only callers have something to mount into). The filter defaults to `true` — empty containers render by default — and themes/consuming plugins never place the block by hand. The block listens to a shared Interactivity API store for toast data.

## Goals / Non-Goals

**Goals:**

- Provide a drop-in toast notification system usable by any WP plugin or theme
- Use the Interactivity API exclusively for reactivity (no external JS frameworks)
- Support arbitrary content in toasts (plain text, HTML markup, action buttons)
- Stack multiple simultaneous toasts with proper ordering
- Auto-dismiss toasts after a configurable timer
- Allow manual dismissal via close button
- Provide both PHP (`wp_tosuto()`) and JS (store action) APIs for creating toasts
- Ship Shadcn-inspired styling with CSS custom properties for customization

**Non-Goals:**

- Not a Gutenberg editor block for content creation — this is a runtime notification system
- No persistent notification storage or database integration
- No admin-area toast system (wp-admin has its own notices) — this targets the frontend
- No drag-to-reorder or interactive toast management
- No toast grouping or categorization beyond variant types

## Decisions

### 1. Single Interactivity API store as the source of truth

All toast state lives in a single `wp-tosuto` store namespace. Any module can dispatch toasts by calling `store('wp-tosuto').actions.add(content, options)` — the same `(content, options)` signature as the PHP `wp_tosuto()` helper.

**Why**: The Interactivity API store is globally accessible across modules. A single namespace avoids coordination problems and makes the API surface predictable. Alternatives like custom events would require extra serialization and wouldn't benefit from the Interactivity API's reactive rendering.

### 2. Block-based container registration

The toaster is registered as a WordPress block (`wp-tosuto/toaster`) with a `"render": "file:./render.php"` property in `block.json`. The render file outputs the container `<div>` with Interactivity API directives. It is a dynamic block with no editor UI — the plugin itself emits it on `wp_footer` (late priority) by calling `do_blocks('<!-- wp:wp-tosuto/toaster /-->')`.

Whether the emission actually happens on a given request is decided by this rule:

1. If the request-scoped toast queue is non-empty, the block is always emitted.
2. Otherwise the plugin applies the `wp_tosuto_render_empty` filter (default `true`) and normalises its return value as follows:
   - `true` → emit an empty container (default behavior, so runtime-only `store('wp-tosuto').actions.add()` calls always have something to mount into).
   - `false` → do not emit; no container, no view script module, no stylesheet.
   - `callable` → the callable is treated as a WordPress template-tag-style conditional (e.g. `'is_singular'`, `'is_single'`, `'is_post_type_archive'`, or any user-supplied closure). The plugin calls it with no arguments and coerces the result to bool; `true` emits an empty container, `false` does not.
   - anything else → coerced to bool.

The filter is applied only in the empty-queue branch; once a toast has been queued the container must always render, so there is nothing to filter.

**Why**: Blocks are WordPress's standard unit for rendering. Using a block gives us automatic script/style enqueueing via `block.json`'s `viewScriptModule` and `style` fields. The `render` property in `block.json` is the declarative way to specify a dynamic block's server-side rendering — it keeps the render file co-located with the block metadata and avoids passing a `render_callback` argument to `register_block_type()`. Blocks are registered in bulk via `wp_register_block_types_from_metadata_collection()` using the `blocks-manifest.php` generated by `@wordpress/scripts build`. This is more performant than individual `register_block_type()` calls and is the recommended approach since WP 6.7. Emitting the block via `do_blocks()` on `wp_footer` (rather than printing raw markup) preserves the full block pipeline: `viewScriptModule` and `style` are enqueued as usual, and the render file in `block.json` stays the single source of truth for the container's markup. Defaulting `wp_tosuto_render_empty` to `true` means the drop-in "just call `actions.add()` from JS" story works out of the box on every frontend request, while the filter lets site owners tighten the scope (`false` on REST-like endpoints, or `'is_singular'` to only mount on singular views) when the extra bytes are not welcome. Accepting a callable as the filter value avoids forcing every caller to wrap `is_*()` checks in a closure while keeping the filter value statically inspectable (a string callable, not an opaque `Closure`). Alternatives considered: (a) rendering unconditionally — removes the escape hatch for performance-sensitive pages; (b) rendering only when non-empty — breaks JS-only toasting on pages that never called `wp_tosuto()`; (c) asking themes or a mu-plugin to place the block — requires out-of-band coordination and breaks the "drop-in" promise.

### 3. Toast identity via unique IDs; `state.toasts` as a `Map<ToastId, Toast>`

Each toast receives a unique ID (`crypto.randomUUID()` or a counter fallback). On the client, `state.toasts` is a `Map<ToastId, Toast>` that starts empty — add creates a new Map via `new Map(state.toasts).set(id, toast)`, remove copies and deletes, and lookup is `state.toasts.has(id)` / `state.toasts.get(id)`. Every mutation reassigns `state.toasts` to a new `Map` instance (immutable-by-replacement) so the Interactivity API's reactive proxy detects the change. The Map is always empty at init; server-queued toasts are read from `getServerState()` and funnelled through `actions.add`, which sanitizes and starts timers via the normal path. The rendering layer (future) will derive an array from the Map (e.g. via `[...state.toasts.values()]`) for `data-wp-each`.

**Why**: A `Map` gives O(1) add/remove/lookup by the toast's natural key, eliminates the `findIndex` scan the array approach required, and makes the id-to-toast relationship explicit in the data structure rather than implicit via a linear search. `Map` is preferred over a plain `Record` because its API (`.has()`, `.get()`, `.set()`, `.delete()`, `.values()`) is purpose-built for keyed collections and avoids the `delete` operator (which triggers `@typescript-eslint/no-dynamic-delete`). The immutable-by-replacement pattern — creating a new `Map` on every mutation rather than mutating in place — is consistent with how `TimerCollection` and `Timer` already work in the store, and ensures the Interactivity API proxy sees the property assignment.

### 4. CSS custom properties for theming

All visual tokens (colors, spacing, radii, shadows, font sizes) are exposed as `--wp-tosuto-*` custom properties on the container element. Default values use Shadcn's design tokens. Themes override by setting these properties on `:root` or the container selector.

**Why**: CSS custom properties are the standard theming mechanism for WordPress blocks. They require no build step to customize and work with the full theming cascade. Alternative: `theme.json` settings — possible for colors, but too limited for the full design token set.

### 5. Position: fixed container with configurable placement

The toast container uses `position: fixed` and is placed at the bottom-right by default. Position is configurable via a `data-position` attribute (`top-left`, `top-right`, `bottom-left`, `bottom-right`, `top-center`, `bottom-center`).

**Why**: Fixed positioning ensures toasts remain visible during scroll. Bottom-right is the most common toast position across web applications.

### 6. PHP API enqueues toasts via Interactivity API state

`wp_tosuto()` called during PHP execution generates a UUID (via `wp_generate_uuid4()`), applies defaults (`variant: 'default'`, `duration: 5000`, `dismissable: true`) for any omitted option, stores the fully-formed entry in a static request-scoped queue, and returns the UUID to the caller. A companion `wp_tosuto_remove($id)` function removes a previously-queued entry from the same static queue. On `wp_footer` (late priority), if the queue is non-empty, PHP hands it to `wp_interactivity_state('wp-tosuto', ['toasts' => $queue])` and then emits the toaster block via `do_blocks('<!-- wp:wp-tosuto/toaster /-->')` — no defaulting, no id assignment, no mutation. If the queue is empty, the plugin consults the `wp_tosuto_render_empty` filter (see §2): by default it emits an empty container anyway so the JS API is always available; sites that set the filter to `false` or to a template-tag conditional that evaluates to `false` get nothing rendered. On the client, `callbacks.init` reads the server-queued toasts via `getServerState()` and funnels each entry through `actions.add`, which sanitizes, inserts into the `Map`, and starts auto-dismiss timers.

**Why**: `wp_interactivity_state()` is the Interactivity API's native mechanism for server-to-client state transfer. The client reads it back via `getServerState()` rather than relying on the merge into `state.toasts`, because `state.toasts` is a `Map` that the Interactivity API's shallow merge does not populate from the server's JSON array — the Map starts empty and is filled exclusively through `actions.add`. Generating the id and applying defaults at queue time (rather than in `wp_footer`) means the entry is final from the moment `wp_tosuto()` returns, which lets the function hand back a stable id and lets `wp_tosuto_remove()` operate on a known-shape array. It also gives third-party code a removal handle for cancelling toasts that a later step in the same request supersedes — symmetry with the JS `actions.add` / `actions.remove` pair, but bounded to the server side. `wp_footer` is reduced to a single flush call, eliminating the previous defaulting pass and removing the asymmetry between PHP-queued and JS-runtime toasts.

### 7. Toast content is sanitized at the store boundary (server: `wp_kses_post`, client: DOMPurify in `actions.add`)

Toast `content` supports HTML, which makes it a natural XSS sink. The plugin sanitizes at the two points where untrusted input enters `state.toasts`:

- **Server path**: `wp_tosuto()` runs each `content` string through `wp_kses_post()` before handing the request-scoped queue to `wp_interactivity_state()`. This is a best-effort server-side guard, not a client-side trust anchor.
- **Client path**: the store sanitizes `content` with DOMPurify (shipped as a view-script-module dependency) inside `actions.add` — the `Toast` constructor runs DOMPurify on the `content` string before the toast enters the Map. Both runtime JS callers and `callbacks.init` (which funnels server-queued toasts through `actions.add`) use this single entry point, making it the sole client-side sanitization boundary. The client does not assume the server sanitized anything.

The renderer still needs to write HTML into the DOM — `data-wp-text` escapes, and `data-wp-bind--*` only binds attributes. The Interactivity API does not expose `directive()` publicly (it is behind the `privateApis` lock), so registering a custom directive is not possible. Instead, the plugin uses `data-wp-watch="callbacks.renderContent"` on each toast element. The callback reads the toast from state via `getContext()` and writes `content` to `getElement().ref.innerHTML`. `data-wp-watch` wraps `useSignalEffect`, which auto-tracks reactive dependencies and re-fires after paint when any accessed signal changes — so when `state.toasts` updates, the callback re-runs and the DOM stays in sync. With sanitization owned by the store (the `Toast` constructor runs DOMPurify on entry), the callback is a plain writer; it does not re-sanitize.

**Why the client sanitizes independently of the server.** A client that trusts the server's sanitizer is only as safe as the weakest producer of `wp_interactivity_state('wp-tosuto', ...)`. A misconfigured `wp_kses_post()` filter, a plugin that pushes toasts directly via its own state hook, or a future caller that bypasses `wp_tosuto()` would all land unsanitized HTML in the store. Because every toast enters the client Map exclusively through `actions.add` → `new Toast(raw)`, and the `Toast` constructor runs DOMPurify on `content`, the client is the authoritative trust boundary for anything that will be written to the DOM — the server's `wp_kses_post` becomes a convenience, not a dependency. The invariant "every entry in `state.toasts` is safe" holds by construction: if you have a `Toast`, it has been sanitized. `wp_kses_post()` matches the allowlist WordPress already uses for post content, and DOMPurify is the de-facto standard for browser-side HTML sanitization.

### 8. Inpsyde Modularity for plugin architecture

The plugin bootstraps via `Inpsyde\Modularity\Package`. PHP server-side code lives under `sources/server/`, with each subdirectory containing a `Module` implementation. The `Package` is created in the main plugin file and all modules are registered via `addModule()` before calling `boot()`. Composer handles autoloading with a PSR-4 mapping from the plugin's root namespace to `sources/server/`.

**Why**: Inpsyde Modularity provides a lightweight, dependency-injection-friendly architecture for WordPress plugins. Each module declares its own services and hooks, keeping concerns separated. This avoids a monolithic plugin file and makes the codebase easier to extend and test. The PSR-4 autoloading eliminates manual `require` statements.

### 9. TypeScript across all client sources, with implementation-internal store types

All files under `sources/client/` are TypeScript (`.ts` for plain modules, `.tsx` if any JSX is ever needed). The repository's `tsconfig.json` already enables strict type checking (`strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, etc.), and the build toolchain (`@wordpress/scripts`) compiles the `.ts` entry points — notably `sources/client/toaster/view.ts` — to the `view.js` that `block.json`'s `viewScriptModule` ultimately references in the build output.

The types that model the `wp-tosuto` store — the toast object shape, the options accepted by `actions.add`, action return types, and the internal timer-tracking shape — live in a sibling module (`sources/client/toaster/types.ts`) rather than inline in `view.ts`. The view module imports them locally but does not re-export them, and the plugin ships no `.d.ts` or `types` entry for third-party consumers. The only public surfaces the plugin contracts for are the runtime `store('wp-tosuto')` namespace on the client and `wp_tosuto()` / `wp_tosuto_remove()` on the server.

**Why TypeScript.** The store coordinates state, timers, sanitization, and a custom directive — a small surface where the common bugs (misspelled option keys, forgetting to clear a timer, letting an unsanitized string slip past the boundary) are exactly the class that editor-grade type checking catches cheaply. Keeping the whole client tree in TS means no split between "typed parts" and "untyped glue" — every new module starts typed.

**Why keep the types out of `view.ts`.** The view module is the hot path that a future contributor reads first to understand behavior — store registration, actions, callbacks, and the directive. Inlining `interface Toast`, `interface ToastOptions`, action signatures, and the timer-entry shape would double the module's length and bury the behavior under declarations. A sibling `internal/types.ts` lets the entry stay focused on what the code does, and lets the type declarations evolve (add an internal field, tighten a union) without producing noisy diffs through the behavior file.

**Why keep the types implementation-internal rather than publishing them.** The plugin's versioned contract is the spec — the runtime `wp-tosuto` store namespace, the documented action signatures, and the PHP helpers. Exporting TypeScript shapes from the package would silently extend that contract: a renamed internal field or a tightened union would become a breaking change for type consumers even when the runtime behavior is unchanged. Third-party code that needs to talk to the store in TS should declare the shape it expects locally (the narrowest type that covers the specced action signatures), which keeps the plugin free to refactor internals without coordinating type-only breaking changes. This is the same trade-off WordPress core makes with most of its JS packages: a runtime contract, not a typed surface.

### 10. `Toast` and `Timer` as entity classes; `TimerCollection` as the store-facing timer API; `ImmutableRecord` as the underlying keyed map

Four companion pieces sit alongside `view.ts` in the toaster directory:

- `toast.ts` — a `Toast` class that owns the invariants of a toast: id generation (fall back to a counter if `crypto.randomUUID` is unavailable), DOMPurify sanitization of `content`, and defaults for omitted options (`variant: 'default'`, `duration: 5000`, `dismissable: true`). Fields are declared `readonly`. All toasts enter the store through `actions.add`, which builds a `new Toast(raw)` — the constructor is the single enforcement point for sanitization and defaulting. `view.ts` never sanitizes, id-generates, or applies defaults on its own — those concerns live in the class.

- `value-objects/timer.ts` — a `Timer` class paired with a `NullTimer` subclass (Null Object pattern). `Timer` owns the invariants of a running auto-dismiss timer: handle, remaining duration, and start timestamp are private; the static `Timer.start(duration, onExpire)` schedules a `setTimeout` when `duration > 0` and returns a `NullTimer` otherwise; `pause()` clears the handle and recomputes `remaining`; `resume(onExpire)` schedules a new `setTimeout` (or invokes `onExpire` immediately when `remaining <= 0`); `clear()` clears the handle if present. `NullTimer` overrides every method as a no-op — `pause`/`resume` return the same null instance, `clear` does nothing.

- `value-objects/timer-collection.ts` — a `TimerCollection` class that wraps `ImmutableRecord<Timer>` and exposes the full timer lifecycle as immutable operations: `schedule(key, duration, onExpire)` starts a timer via `Timer.start` and returns a new collection (or `this` when the duration is null/zero); `pause(key)` pauses the entry; `resume(key, onExpire)` resumes it; `clear(key)` clears the handle and removes the entry. Each method absorbs the null-entry logic internally — using a module-level `NullTimer` sentinel and the `ImmutableRecord.get(key, fallback)` overload — so consumers never handle `undefined`. The module-level `timers` binding in `view.ts` is a `TimerCollection`, and store actions are plain reassignments: `timers = timers.schedule(id, duration, onExpire)`, `timers = timers.pause(id)`, etc.

- `value-objects/immutable-record.ts` — a small `ImmutableRecord<T>` class modeled on the pattern used in the sibling `Spaghetti-Dojo/kensaku` project (`sources/client/src/models/immutable-record.ts`). It wraps a `Readonly<Record<string, T>>` and exposes `get(key, fallback?)`, `set(key, value)` (returns a new record), and `delete(key)` (returns a new record without the key). Its only consumer today is `TimerCollection`.

**Why an entity class for `Toast`.** Sanitization and defaulting are invariants of a valid toast — they should not be re-derived at every call site. When both `actions.add` and `callbacks.init` built toast POJOs inline, it was easy to diverge (the current `view.js` implementation already had subtle duplication between the two paths). A constructor is the single enforcement point: "if you can hold a `Toast`, it has been sanitized and defaulted." The plain-POJO alternative would have required a freestanding `makeToast()` factory, which is the same thing with weaker grouping — the class keeps the invariants visibly attached to the type.

**Why a value object for `Timer` (and a `NullTimer` counterpart).** The timer lifecycle — schedule, pause, resume, cancel — is a small but non-trivial state machine: a paused entry has a `null` handle and a recomputed `remaining`; a resumed entry re-captures `startedAt`; `clearTimeout` must run on cancel. Moving the state into a `Timer` class lets each transition enforce its own preconditions. `NullTimer` absorbs both the "no entry for this id" and the "entry exists but operation is a no-op here" cases (e.g. pausing an already-paused timer), and keeps the timer internals private — `handle`, `remaining`, and `startedAt` are `#private` fields, so no call site can reach in and mutate them.

**Why `TimerCollection` sits between `view.ts` and the lower-level `Timer` / `ImmutableRecord` pieces.** Before this layer existed, `view.ts` imported `ImmutableRecord`, `Timer`, `NullTimer`, and a standalone `scheduleTimer()` helper — four imports and scattered null-checking across every store action. `TimerCollection` collapses that into a single import whose methods mirror the store's intent (`schedule`, `pause`, `resume`, `clear`) and return a new collection on every call. The null-entry bookkeeping is fully internal: the store never sees `NullTimer`. This also keeps `ImmutableRecord` and `Timer` as purely internal building blocks — they are implementation details of the collection, not part of the store's vocabulary.

**Why `ImmutableRecord` for the underlying keyed map.** A built-in `Map<K, V>` supports in-place mutation (`map.set`, `map.delete`) — which conflicts with the project-wide rule that client-side state is updated by replacement, not field mutation (see the `Toast` / `Timer` immutability pattern). `ImmutableRecord` makes the replacement explicit and keeps the map uniform with the rest of the client state. Keeping the API Map-like (`get` / `set` / `delete`) matches the kensaku reference so contributors familiar with that pattern recognize it immediately. Performance is a non-issue at the expected map sizes (< 10 live timers in typical use).

**Why `Timer` and `NullTimer` share a file despite the project's `max-classes-per-file` rule.** The two classes are a single Null Object pattern — `Timer.start` / `pause` / `resume` all construct `new NullTimer()`, and `NullTimer extends Timer`. Splitting them into two modules creates a true ES-module circular dependency at class-initialization time (loading `null-timer.ts` would evaluate `class NullTimer extends Timer {...}` before `timer.ts` finishes exporting `Timer`, triggering a TDZ error). The file carries a targeted `eslint-disable max-classes-per-file` with a comment explaining the pairing; the rule still applies to the rest of the codebase.

**Why the classes, collection, and record live in the same folder as `view.ts`, not in a shared utilities location.** All four are toaster-specific: `Toast` encodes the toaster's domain, `Timer` encodes the timer state machine used only by the toaster's auto-dismiss, `TimerCollection` is the store-facing facade for that state machine, and `ImmutableRecord`'s only consumer today is `TimerCollection`. Promoting any of them to a shared location would be premature. If a second block ever needs the same patterns, we can hoist them then.

## Risks / Trade-offs

- **Interactivity API maturity**: The API is stable in WP 6.9+ but less battle-tested than React. Mitigation: stick to documented store/directive APIs, avoid internal details.
- **Multiple container instances**: The plugin is the only emitter of the toaster block (via `wp_footer`), so duplication is not expected in normal use. As a belt-and-braces guard, the render file still checks a static flag and outputs markup at most once per request, which also protects against a theme or third-party explicitly re-inserting `<!-- wp:wp-tosuto/toaster /-->` in content.
- **JS-only toasts on pages with no server-queued toast**: Handled by the `wp_tosuto_render_empty` filter, which defaults to `true` so the empty container is rendered on every frontend request and JS-only `store('wp-tosuto').actions.add(...)` calls always have a mount point. Sites that narrow the filter (e.g. to `'is_singular'` or `false`) accept that pages outside the chosen scope will not host runtime toasts; this is an explicit opt-out, not a silent constraint.
- **Arbitrary callables in the filter**: Accepting a callable means third-party code can pass any `callable` and have it invoked on every frontend `wp_footer`. Mitigation: the plugin calls the value via `call_user_func()` with no arguments, coerces the result to `bool`, swallows no exceptions, and documents that the callable is expected to be a cheap read-only conditional (the WP template tags are the canonical example). It is not a filter chain and it is not passed any toast data.
- **Timer cleanup on navigation**: If the site uses client-side navigation (Interactivity API regions), timers from a previous page could fire. Mitigation: clear all timers in a `beforeunload` or navigation callback.
- **Accessibility**: Toasts that auto-dismiss can be problematic for screen readers. Mitigation: use `role="status"` and `aria-live="polite"` on the container so content is announced, and pause auto-dismiss on hover/focus.
