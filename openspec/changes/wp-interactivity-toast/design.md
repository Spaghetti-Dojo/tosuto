## Context

This is a greenfield WordPress plugin (`wp-toast`) targeting WordPress 6.9+. The plugin provides a toast notification component built entirely on the Interactivity API — no jQuery, no React on the frontend. The Interactivity API provides reactive state management via stores, declarative directives (`data-wp-*`) in server-rendered HTML, and automatic DOM updates. The design follows Shadcn's philosophy: minimal, composable, themeable via CSS custom properties.

The plugin consists of a single WordPress block (`wp-toast/toaster`) that acts as the toast container. The plugin renders this block automatically on `wp_footer` at a late priority. If the request-scoped queue is non-empty, the block is always rendered. If the queue is empty, the `wp_toast_render_empty` filter decides whether to still render an empty container (so JS-only callers have something to mount into). The filter defaults to `true` — empty containers render by default — and themes/consuming plugins never place the block by hand. The block listens to a shared Interactivity API store for toast data.

## Goals / Non-Goals

**Goals:**

- Provide a drop-in toast notification system usable by any WP plugin or theme
- Use the Interactivity API exclusively for reactivity (no external JS frameworks)
- Support arbitrary content in toasts (plain text, HTML markup, action buttons)
- Stack multiple simultaneous toasts with proper ordering
- Auto-dismiss toasts after a configurable timer
- Allow manual dismissal via close button
- Provide both PHP (`wp_toast()`) and JS (store action) APIs for creating toasts
- Ship Shadcn-inspired styling with CSS custom properties for customization

**Non-Goals:**

- Not a Gutenberg editor block for content creation — this is a runtime notification system
- No persistent notification storage or database integration
- No admin-area toast system (wp-admin has its own notices) — this targets the frontend
- No drag-to-reorder or interactive toast management
- No toast grouping or categorization beyond variant types

## Decisions

### 1. Single Interactivity API store as the source of truth

All toast state lives in a single `wp-toast` store namespace. Any module can dispatch toasts by calling `store('wp-toast').actions.add(content, options)` — the same `(content, options)` signature as the PHP `wp_toast()` helper.

**Why**: The Interactivity API store is globally accessible across modules. A single namespace avoids coordination problems and makes the API surface predictable. Alternatives like custom events would require extra serialization and wouldn't benefit from the Interactivity API's reactive rendering.

### 2. Block-based container registration

The toaster is registered as a WordPress block (`wp-toast/toaster`) with a `"render": "file:./render.php"` property in `block.json`. The render file outputs the container `<div>` with Interactivity API directives. It is a dynamic block with no editor UI — the plugin itself emits it on `wp_footer` (late priority) by calling `do_blocks('<!-- wp:wp-toast/toaster /-->')`.

Whether the emission actually happens on a given request is decided by this rule:

1. If the request-scoped toast queue is non-empty, the block is always emitted.
2. Otherwise the plugin applies the `wp_toast_render_empty` filter (default `true`) and normalises its return value as follows:
   - `true` → emit an empty container (default behavior, so runtime-only `store('wp-toast').actions.add()` calls always have something to mount into).
   - `false` → do not emit; no container, no view script module, no stylesheet.
   - `callable` → the callable is treated as a WordPress template-tag-style conditional (e.g. `'is_singular'`, `'is_single'`, `'is_post_type_archive'`, or any user-supplied closure). The plugin calls it with no arguments and coerces the result to bool; `true` emits an empty container, `false` does not.
   - anything else → coerced to bool.

The filter is applied only in the empty-queue branch; once a toast has been queued the container must always render, so there is nothing to filter.

**Why**: Blocks are WordPress's standard unit for rendering. Using a block gives us automatic script/style enqueueing via `block.json`'s `viewScriptModule` and `style` fields. The `render` property in `block.json` is the declarative way to specify a dynamic block's server-side rendering — it keeps the render file co-located with the block metadata and avoids passing a `render_callback` argument to `register_block_type()`. Blocks are registered in bulk via `wp_register_block_types_from_metadata_collection()` using the `blocks-manifest.php` generated by `@wordpress/scripts build`. This is more performant than individual `register_block_type()` calls and is the recommended approach since WP 6.7. Emitting the block via `do_blocks()` on `wp_footer` (rather than printing raw markup) preserves the full block pipeline: `viewScriptModule` and `style` are enqueued as usual, and the render file in `block.json` stays the single source of truth for the container's markup. Defaulting `wp_toast_render_empty` to `true` means the drop-in "just call `actions.add()` from JS" story works out of the box on every frontend request, while the filter lets site owners tighten the scope (`false` on REST-like endpoints, or `'is_singular'` to only mount on singular views) when the extra bytes are not welcome. Accepting a callable as the filter value avoids forcing every caller to wrap `is_*()` checks in a closure while keeping the filter value statically inspectable (a string callable, not an opaque `Closure`). Alternatives considered: (a) rendering unconditionally — removes the escape hatch for performance-sensitive pages; (b) rendering only when non-empty — breaks JS-only toasting on pages that never called `wp_toast()`; (c) asking themes or a mu-plugin to place the block — requires out-of-band coordination and breaks the "drop-in" promise.

### 3. Toast identity via unique IDs

Each toast receives a unique ID (`crypto.randomUUID()` or a counter fallback). The store maintains a `state.toasts` array ordered by creation time (newest last). Removal is by ID, which keeps operations O(n) but n is small (typically < 10 toasts).

**Why**: Numeric indices shift when toasts are removed mid-stack. UUIDs give stable references for timers and dismiss callbacks.

### 4. CSS custom properties for theming

All visual tokens (colors, spacing, radii, shadows, font sizes) are exposed as `--wp-toast-*` custom properties on the container element. Default values use Shadcn's design tokens. Themes override by setting these properties on `:root` or the container selector.

**Why**: CSS custom properties are the standard theming mechanism for WordPress blocks. They require no build step to customize and work with the full theming cascade. Alternative: `theme.json` settings — possible for colors, but too limited for the full design token set.

### 5. Position: fixed container with configurable placement

The toast container uses `position: fixed` and is placed at the bottom-right by default. Position is configurable via a `data-position` attribute (`top-left`, `top-right`, `bottom-left`, `bottom-right`, `top-center`, `bottom-center`).

**Why**: Fixed positioning ensures toasts remain visible during scroll. Bottom-right is the most common toast position across web applications.

### 6. PHP API enqueues toasts via Interactivity API state

`wp_toast()` called during PHP execution generates a UUID (via `wp_generate_uuid4()`), applies defaults (`variant: 'default'`, `duration: 5000`, `dismissable: true`) for any omitted option, stores the fully-formed entry in a static request-scoped queue, and returns the UUID to the caller. A companion `wp_toast_remove($id)` function removes a previously-queued entry from the same static queue. On `wp_footer` (late priority), if the queue is non-empty, PHP hands it to `wp_interactivity_state('wp-toast', ['toasts' => $queue])` and then emits the toaster block via `do_blocks('<!-- wp:wp-toast/toaster /-->')` — no defaulting, no id assignment, no mutation. If the queue is empty, the plugin consults the `wp_toast_render_empty` filter (see §2): by default it emits an empty container anyway so the JS API is always available; sites that set the filter to `false` or to a template-tag conditional that evaluates to `false` get nothing rendered. The store's `init` callback iterates `state.toasts` and starts auto-dismiss timers for any toast with `duration > 0`.

**Why**: `wp_interactivity_state()` is the Interactivity API's native mechanism for server-to-client state transfer. Generating the id and applying defaults at queue time (rather than in `wp_footer`) means the entry is final from the moment `wp_toast()` returns, which lets the function hand back a stable id and lets `wp_toast_remove()` operate on a known-shape array. It also gives third-party code a removal handle for cancelling toasts that a later step in the same request supersedes — symmetry with the JS `actions.add` / `actions.remove` pair, but bounded to the server side. `wp_footer` is reduced to a single flush call, eliminating the previous defaulting pass and removing the asymmetry between PHP-queued and JS-runtime toasts. The only thing PHP cannot do is start timers; `init` handles that for any toasts already present at hydration time.

### 7. Toast content is sanitized at the store boundary (server: `wp_kses_post`, client: DOMPurify in `actions.add`)

Toast `content` supports HTML, which makes it a natural XSS sink. The plugin sanitizes at the two points where untrusted input enters `state.toasts`:

- **Server path**: `wp_toast()` runs each `content` string through `wp_kses_post()` before handing the request-scoped queue to `wp_interactivity_state()`. This is a best-effort server-side guard, not a client-side trust anchor.
- **Client path**: the store sanitizes `content` with DOMPurify (shipped as a view-script-module dependency) in two places — inside `actions.add` before appending a new toast, and inside `callbacks.init` where it walks `state.toasts` and re-sanitizes every hydrated entry in place. The client does not assume the server sanitized anything.

The renderer still needs to write HTML into the DOM — `data-wp-text` escapes, and `data-wp-bind--*` only binds attributes — so the plugin exposes HTML through a single custom Interactivity API directive (e.g. `data-wp-toast--html`) whose callback is the one and only place an `innerHTML` write happens. With sanitization owned by the store, that callback is a plain writer; it does not re-sanitize.

**Why the client re-sanitizes hydrated toasts instead of trusting the server.** A client that trusts the server's sanitizer is only as safe as the weakest producer of `wp_interactivity_state('wp-toast', ...)`. A misconfigured `wp_kses_post()` filter, a plugin that pushes toasts directly via its own state hook, or a future caller that bypasses `wp_toast()` would all land unsanitized HTML in `state.toasts`. Re-running DOMPurify on hydrated entries in `callbacks.init` makes the client the authoritative trust boundary for anything that will be written to the DOM — the server's sanitizer becomes a convenience, not a dependency. Doing it in `init` (rather than at render time) keeps the invariant "every entry in `state.toasts` is safe" true for every consumer, not just the renderer. `wp_kses_post()` matches the allowlist WordPress already uses for post content, and DOMPurify is the de-facto standard for browser-side HTML sanitization.

### 8. Inpsyde Modularity for plugin architecture

The plugin bootstraps via `Inpsyde\Modularity\Package`. PHP server-side code lives under `sources/server/`, with each subdirectory containing a `Module` implementation. The `Package` is created in the main plugin file and all modules are registered via `addModule()` before calling `boot()`. Composer handles autoloading with a PSR-4 mapping from the plugin's root namespace to `sources/server/`.

**Why**: Inpsyde Modularity provides a lightweight, dependency-injection-friendly architecture for WordPress plugins. Each module declares its own services and hooks, keeping concerns separated. This avoids a monolithic plugin file and makes the codebase easier to extend and test. The PSR-4 autoloading eliminates manual `require` statements.

## Risks / Trade-offs

- **Interactivity API maturity**: The API is stable in WP 6.9+ but less battle-tested than React. Mitigation: stick to documented store/directive APIs, avoid internal details.
- **Multiple container instances**: The plugin is the only emitter of the toaster block (via `wp_footer`), so duplication is not expected in normal use. As a belt-and-braces guard, the render file still checks a static flag and outputs markup at most once per request, which also protects against a theme or third-party explicitly re-inserting `<!-- wp:wp-toast/toaster /-->` in content.
- **JS-only toasts on pages with no server-queued toast**: Handled by the `wp_toast_render_empty` filter, which defaults to `true` so the empty container is rendered on every frontend request and JS-only `store('wp-toast').actions.add(...)` calls always have a mount point. Sites that narrow the filter (e.g. to `'is_singular'` or `false`) accept that pages outside the chosen scope will not host runtime toasts; this is an explicit opt-out, not a silent constraint.
- **Arbitrary callables in the filter**: Accepting a callable means third-party code can pass any `callable` and have it invoked on every frontend `wp_footer`. Mitigation: the plugin calls the value via `call_user_func()` with no arguments, coerces the result to `bool`, swallows no exceptions, and documents that the callable is expected to be a cheap read-only conditional (the WP template tags are the canonical example). It is not a filter chain and it is not passed any toast data.
- **Timer cleanup on navigation**: If the site uses client-side navigation (Interactivity API regions), timers from a previous page could fire. Mitigation: clear all timers in a `beforeunload` or navigation callback.
- **Accessibility**: Toasts that auto-dismiss can be problematic for screen readers. Mitigation: use `role="status"` and `aria-live="polite"` on the container so content is announced, and pause auto-dismiss on hover/focus.
